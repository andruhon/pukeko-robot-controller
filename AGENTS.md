# AGENTS.md — Pukeko Robot Controller

A Vue web UI + AG-UI backend that lets an LLM drive an Acebott biped robot in front of a webcam. Tuned to work well with local Gemma 4 via Ollama; also runs against Claude (Anthropic) and the robot stub.

## Run

```sh
# robot stub (port 8080)
pnpm run stub

# grid-world emulator, an alternative to the stub (ROBOT_EMULATOR_PORT, default 8081)
pnpm run emulator

# AG-UI backend (port 3000)
ROBOT_HOST=localhost:8080 pnpm run server

# web UI (port 5173)
pnpm run dev:ag-ui
```

Real robot: skip `pnpm run stub` and connect to the robot's Wi-Fi AP. Set `ROBOT_HOST=192.168.4.1` (default) or whatever IP it picks up.

## Choosing a world

The nav header's **World** picker chooses what the student is actually driving: the real robot, or the grid-world emulator. It is a robot-*target* choice, not a camera one — the motion endpoints and the frames both follow it, because a simulated world only advances when `/forward` and friends reach the emulator. Switching re-instantiates the `RobotSession` (its `robotHost` is readonly) and remounts the chat with a clean message log, exactly as a preset switch does.

The browser reaches each world at a build-time host: `VITE_ROBOT_HOST` (default `192.168.4.1`) for the real robot, `VITE_ROBOT_EMULATOR_HOST` (default `localhost:8081`, matching `ROBOT_EMULATOR_PORT`'s default) for the emulator. In the simulated world the Cockpit shows the last frame the emulator served — refreshed whenever the app fetched one anyway, never on a timer — and never the live webcam. The `<PkWebcamPanel>` stays mounted with its stream stopped: the motion recipes' Before/After composite is drawn on that component's hidden canvas.

## The two fake robots

- **`robot-stub/`** — a **protocol** stub. It echoes each command back and returns a jittered fake `/distance`; it has no idea where the robot is. Its predictability is the point: the browser e2e boots it. Keep it this dumb.
- **`robot-emulator/`** — an **emulator**. Same endpoints, same steps clamping, same CORS, but backed by a real continuous pose on a tiled world (`world.ts`, pure and map-driven), with `/distance` measured rather than faked and a `GET /capture` that renders the world as a real JPEG (`render.ts`).
  - **Centimetres are the unit; tiles are only how a map is drawn.** Terrain is still rows of legend characters, and the tile's own size is one more setting in centimetres (default 5, so the shipped 14×12 arena is 70×60 cm — the size of the real one). Everything else — body, stride, pose, sensor range — is centimetres, so how many tiles a body covers is derived, never configured. Field names carry the unit (`xCm`, `headingDeg`, `widthTiles`); keep it that way, because a bare number that used to mean tiles and now means centimetres type-checks and is wrong by the tile size. A map's start is the one field that names a **tile** — write it as `start: { xTiles, yTiles, headingDeg }`, where `headingDeg` is degrees clockwise from north and any angle is valid, not just the four compass points; a map authored to any other shape does not load.
  - **The hardware comes from the robot preset** (`src/agent/robotPresets/physical.ts`), so the robot the emulator simulates and the robot the prompt describes are the same robot by construction: 10 cm body, 1.5 cm forward and 1.3 cm backward per gait cycle, 15° per turn cycle, 1.5% jitter, a 3 cm sensor floor. A preset that states nothing gets those; a different robot states only what differs. Those figures are also written as **prose** the model reads — `system-prompt.md` and the tool descriptions — and `tests/calibrationProse.test.ts` parses them back out of that prose and compares them to the profile, so a recalibration the prose has not followed fails a test naming the figure and both values. When it fires, **the prose is what moves**: the profile's numbers are the hardware's.
  - `state.xCm, state.yCm` is the body **centre** and `headingDeg` is degrees clockwise from north. Motion is applied **one gait cycle at a time**, and each cycle tests the **swept body** against the tiles it overlaps — any overlap with a wall or the world edge blocks (a truthful no-op the run survives), any overlap with a soft tile snags, and the abyss is fatal when the **centre** crosses in, so a wheel over the lip does not end the run. That rule lives in `probeSweptBody` and is tested on its own.
  - **Jitter is seeded**, the seed lives in the state, and `jitterFraction: 0` gives exact motion. `Math.random()` in `world.ts` is a defect. The observation reports the **command**, never the distance achieved: a real robot has no odometry and practising without it is the point.
  - The robot is drawn as the real overhead **photograph** of the chassis (`robot-emulator/assets/`), pre-rotated into 24 orientations (one per turn cycle) so a frame stays a blit, drawn at its centimetre size and at a sub-tile position, and composited with alpha — a vision model does not recognise a flat marker as a robot, and finding itself in the frame is the first thing every navigation prompt asks it to do.
  - Death ends the run through the observation only — no hidden field yanks the control loop; the model reads that the robot is destroyed and calls its completion tool to declare failure. The camera view is 3rd-person overhead, which is **not** what the robot's onboard camera sees — see the trade-off recorded in `render.ts`.
- **`robot-protocol/`** — what the two share: the endpoint lists, `MAX_STEPS`, the steps clamp and the CORS middleware. They live here rather than in either server because two copies drift, and an emulator that has quietly stopped matching the firmware still looks correct in isolation.

## Architecture

- **`server/index.ts`** — boots `@gaunt-sloth/agent` AG-UI server. Wires LLM, tools, and middleware.
- **`src/agent/robotPresets/`** — **RC-1**: the robot-preset mechanism. A "preset" is a named, data-driven tool set tied to one hardware variant (`RobotPreset { id, name, hardwareId, tools: RobotToolDef[] }` in `types.ts`). `index.ts` is the registry (`getRobotPreset(id)`, `DEFAULT_ROBOT_PRESET_ID`, `getClientToolDefs(id)`); `acebottQd021.ts` is the one shipped preset today, reproducing the original hardcoded 8-tool set byte-for-byte. Each `RobotToolDef` carries **two** representations of its parameter schema side by side on purpose — `zodSchema` (drives the server-side LangChain tool) and `jsonSchema` (registered by the browser client as an AG-UI `Tool.parameters` value for client-fulfilled tools) — so they can't drift the way the pre-RC-1 duplication between `robotTools.ts` and `App.vue` could. **Leaf module**: only depends on `zod` + `robotToolNames.ts`, never `robotTools.ts`/Node builtins — `App.vue` imports it straight into the browser bundle. A robot model selects its preset via `robot.preset` in `pukeko.config.ts` (server, default `ACEBOTT-QD021`) / `VITE_ROBOT_PRESET` (client, same default) — see Conventions below. A second preset (different hardware, different tool set) is a follow-up; this increment ships exactly one.
- **`src/agent/robotTools.ts`** — turns a preset's declarative `RobotToolDef[]` into runnable server-side `StructuredTool`s (`createRobotTools(host, presetId)`).
  - **Motion tools** (`move_forward`, `move_backward`, `turn_left`, `turn_right`) are **client-fulfilled** (`metadata: { client: true }`), driven by `fulfillment: 'client'` on the tool's preset def. The browser orchestrates the whole capture+move+capture+compose sequence — see below.
  - **Sensor & control tools** (`read_distance`, `read_status`, `stop`) stay server-side and hit the robot's HTTP API directly, via each def's `serverPath` (e.g. `read_distance` → `/distance` — **not** derivable from the tool name, the mapping is asymmetric per tool).
  - **`capture_image`** is the standalone client-fulfilled camera tool, kept for mid-sequence alignment checks — outside the preset (it's hardware-agnostic, not part of the ACEBOTT-QD021 tool-set extraction). **PLAT-18**: its declaration + capture handler now live in `@galvanized-pukeko/vue-ui` (`createCaptureImageToolDeclaration` / `captureImageResult`); `RobotSession` consumes them with a robot-flavoured description override. There is **no server-side stub any more** — the UI declares the tool in every AG-UI run-input and the gaunt-sloth server binds run-input tools as `metadata.client` interrupt stubs itself (the old static `captureImageTool.ts` stub was already being filtered out in favour of that dynamic binding on every UI run).
  - **`finish_task`** is the agent's **structured terminal action** — the only intended way to end a run. Server-fulfilled, no robot side effect, special-cased by name in `robotTools.ts` (the one genuinely non-generic "terminal" tool). It's marked **`returnDirect: true`**, which is what actually stops the graph: `createAgent` routes straight to END after a returnDirect tool runs (matching on the ToolMessage name), instead of looping the result back to the model. **Do not** try to end from a tool with `Command({ goto: END })` — `createAgent` ignores it and the run grinds to the recursion limit. `status` is `success | failed | need_input`; a required one-line `summary` says what was achieved or what's blocking. The "do a real action before giving up" rule is **prompt-level** guidance (not a hard runtime gate — a per-tool `returnDirect` can't both reject and continue); `motionLog`'s `hasRunRealTool` flag remains available should a middleware-enforced gate be wanted later.
- **`src/agent/robotToolNames.ts`** / **`src/agent/motionLog.ts`** — `robotToolNames` is a tiny leaf module holding the motion/`finish_task` tool-name constants (so `robotTools` can depend on `motionLog` without a cycle). `motionLog` is the deterministic, process-memory loop state keyed by `thread_id`: the recent-motion log (immune to summary drift), the `finish_task` give-up gate, and the pinned calibration line. `observeAssistantMessage` is called once per assistant turn from each pruning middleware's `afterModel`; `formatPinnedState` is appended to the summary by both so the durable facts survive a prune.
- **`src/agent/frontendImageInjectionMiddleware.ts`** — converts the JSON envelope `{ mimeType, data, motion }` that comes back from `capture_image` / motion tools into a provider-shaped `HumanMessage` content block (Ollama: `image_url`; Anthropic: `image`). For motion envelopes it labels the block `Before/After frames for <motion>.`. (The motion tools do **not** capture distance — the model calls `read_distance` itself; there is no auto-stamped sensor line.)
- **`src/agent/motionSummarizationMiddleware.ts`** — concurrent-with-motion history compression. `afterModel` detects a motion tool call in the assistant message and immediately fires a summarization LLM call (uses the same `llm`). `beforeModel` on the next turn awaits the summary and rewrites the message history to keep only: the original user prompt verbatim, a single `SystemMessage` summary, and the most recent motion turn cluster.
- **`src/agent/contextPrunerMiddleware.ts`** — mechanical alternative to `motion-summary`. `beforeModel` strips base64 `data` from motion/capture `ToolMessage`s (the image rides in the next `HumanMessage` anyway), keeps only the latest N image-bearing `HumanMessage`s, and drops stale `reasoning_content` from older AI turns — preserving reasoning text and tool calls verbatim. It only fires the summarizer LLM when pruned history crosses `summarizeAtFraction × maxContextTokens`. Its `afterModel` records loop state into `motionLog`, and when it summarizes it appends `formatPinnedState` (recent-motion log + calibration) to the summary — so, like `motion-summary`, it never erases the attempted-motion record. **Rewritten messages must keep their original `id`** — `add_messages` assigns fresh UUIDs to id-less messages after `RemoveMessage(REMOVE_ALL)`, which breaks the AG-UI client's dedup-by-id and double-renders tool cards. Mutually exclusive with `motion-summary` (both rewrite the head on `beforeModel`).
- **`src/agent/lazyToolRecoveryMiddleware.ts`** — counters small-local-model laziness: Gemma/Gemini often *narrate* a tool ("`read_distance` to check the range.") and end the turn without emitting the call, stalling the run. `wrapModelCall` inspects the reply; on a no-tool answer that names a known tool it runs a cheap **isolated** classifier call (`callbacks: []`, detached from streaming) asking whether a tool was intended, then re-invokes **through the framework `handler`** (not a hand-built message) so the recovered tool call streams as real `TOOL_CALL_*` events the client run loop can fulfil. `done_reason: 'length'` (Ollama output-cap truncation) is treated as a cutoff, not laziness, and left alone. Knobs: `maxRecoveries` (default 1, or 2 when `force`), `skipClassifier` (recover on any tool-name mention, no classifier round-trip), `force` (harshest — re-prompt on ANY no-tool reply, even one naming no tool; the model must call some tool every turn, leaning on `finish_task` as the always-available "done" tool; this is the Ollama-path equivalent of forcing tool_choice). **Still required for the Ollama/Gemma path:** tool choice is `auto` on every provider (see `tool_choice` below — forcing was removed because it made the hosted models mute and loopy), so the narrate-but-don't-call stall is possible on any path and this middleware is the net for all of them. (ChatOllama can't be forced anyway — `tool_choice?: never`.)
- **`src/App.vue` + `src/components/WebcamPanel.vue`** — Vue UI. Camera capture happens in the hidden `<canvas>` in `WebcamPanel`. `App.vue` derives its `clientTools` (registered with `@galvanized-pukeko/vue-ui`'s `ChatInterface`) and `clientToolHandlers` from `getClientToolDefs()` (RC-1) instead of hand-duplicating tool metadata — each motion tool's HTTP path comes from the preset def's `clientEndpoint` (e.g. `move_forward` → `/forward`). The motion-tool handlers fetch the robot directly (`http://${VITE_ROBOT_HOST}${clientEndpoint}?steps=N`), capture Before/After frames, and compose them via `WebcamPanel.composeBeforeAfter`. **Requires CORS on the robot** — both `robot-stub/robotStub.ts` and `acebot-biped/for-agents/Biped_Robot_Web.py` send `Access-Control-Allow-Origin: *`.

## Committing

**Write the commit message to a file and commit with `git commit -F <file>` — never `git commit
-m`.** This is a hard safety rule, not a style preference. Inside double quotes bash treats a
backtick or `$(…)` as **shell command substitution**, so a message that quotes code the way ordinary
prose does is *executed* before git ever runs; that failure has already destroyed a working tree on
a developer machine. A file path carries no shell metacharacters, so with `-F` no part of the
message can reach a shell — and multi-paragraph bodies, quotes and trailers survive with no
escaping.

- **Create the message file with your file-write tool** — never `echo "..." > msg.txt` and never an
  unquoted heredoc. Both put the identical prose back into a shell argument one layer up, which is
  where this hazard silently returns.
- Messages are plain English: what changed and why. No code, no shell commands, no backticks, no
  markup.
- The same applies to any long prose on a command line — prefer `gh pr create --body-file` and
  `gh release create --notes-file` over `--body` / `--notes`.

## Conventions worth knowing

- Default model: Gemma 4 via Ollama (`OLLAMA_MODEL=gemma4:12b`). 12b rather than 31b because 31b is ~21.5 GB loaded and does not fit the dev box's 15.9 GiB GPU at any context window — a third of it runs on CPU and first token takes 17–19 s against 12b's ~4 s. Optimized for small models — the motion-tools auto-capture + summarization combo means the LLM doesn't have to remember to bracket motions with `capture_image` and the context window stays trim.
- **The ollama context window and the pruner's budget are one decision, not two.** A local profile sets `llm.ollama.numCtx` (`num_ctx`) at or above its `contextPruner.maxContextTokens`; the shipped local profiles use 32768 against a 30000 cap. Left unset, a stock ollama serves 4096 and silently discards everything past it **from the head** — where the opening instruction, the system framing and the pruner's own summary sit — so the pruner spends its budget on history the model never receives. `loadConfig` warns once at startup when the two disagree (`contextWindowWarning` in `server/loadConfig.ts`); raising `numCtx` on `gemma4:12b` is nearly free (4096 → 32768 cost 0.3 GB and stayed 100% on the GPU).
- Providers (`server/createLlm.ts`): `ollama`, `anthropic`, `openai`, `openrouter`, and `google` (native Google AI Studio / Gemini via `@langchain/google`, `platformType: 'gai'`, key from `GOOGLE_API_KEY`). Override per run with `LLM_PROVIDER` + the provider's `*_MODEL` env (e.g. `LLM_PROVIDER=google GOOGLE_MODEL=gemini-3.1-flash-lite`). Gemini's `tool_choice` is call-time-only in `ChatGoogle`, so the google path is constructed without forcing — like everything else, it's `auto`.
- Parallel tool calls are **disabled** on Anthropic (`disable_parallel_tool_use: true` in `server/createLlm.ts`) because client-fulfilled tools rely on a LangGraph interrupt and parallel batching breaks the resume ordering.
- **Tool choice is `auto`, NOT forced** (`tool_choice: 'auto'` in `server/createLlm.ts`). Forcing a tool every turn ("any"/"required") was tried — the idea was that the loop always ends via `finish_task`, so the model never needs a no-tool reply to terminate. In practice it backfired badly on hosted models: the agent could then **never emit a plain-text reply** (every turn was a tool-only message, so the UI looked like it "doesn't talk"), and with no "just answer / stop" escape hatch it **looped on a tool** — usually `capture_image` — when uncertain, instead of reading a sensor or finishing. So all providers now use `auto`: the model talks when it should, acts when it should, and ends naturally. The narrate-but-don't-call stall (the original reason for forcing) is covered by the `lazy-tool-recovery` middleware. `disable_parallel_tool_use` / `parallel_tool_calls: false` is still set — that's a separate control (one tool per turn for interrupt ordering) and is unrelated to forcing.
- **`recursionLimit`** is set to `64` in `server/index.ts` (gaunt-sloth's default is 1000). It caps the agent's super-steps per run so a stuck embodied loop fails fast and visibly instead of grinding ~1000 local inferences. Plumbed through gaunt-sloth's `GthConfig.recursionLimit` → `getNewRunnableConfig(recursionLimit)` → the AG-UI run config.
- The agent's behavioural prompt lives in `system-prompt.md` at the repo root (the operating mindset, calibration sequence, distance-sensor caveats). Update there, not in code, when changing how the agent thinks. It's loaded via gaunt-sloth's configurable `prompts.guidelines` slot (set in `server/index.ts`), overridable per profile with `systemPromptPath`.
- The motion-summarization prompt lives in `summarization-prompt.md` at the repo root (what each compressed history must carry forward — objective, calibration outcomes, action log, findings). Overridable per profile with `summaryPromptPath`. `src/agent/motionSummarizationMiddleware.ts` keeps an identical `DEFAULT_SUMMARY_PROMPT` as a fallback for when the file is absent — keep the two in sync.
- Briefs in `_briefs/` describe planned/completed work. `01-*` documented the `capture_image` interrupt/resume flow; `02-*` documented the motion-tool auto-capture and summarization work that this AGENTS.md describes; `03-*` reviewed the agentic loop (termination, exits, memory durability) and motivated `finish_task`, the shared `motionLog`, forced tool choice, and the `recursionLimit` cap.
- **Robot preset selection (RC-1)**: server-side, set `robot: { preset: 'ACEBOTT-QD021' }` in a `pukeko.config.ts` profile or override with `ROBOT_PRESET=<id>`; client-side (Vite build), set `VITE_ROBOT_PRESET=<id>`. Both independently default to `ACEBOTT-QD021`; there's no runtime check that they agree — if they ever disagree the browser would register a different tool set than the server expects. That's a known seam for GS2-10 (cross-repo config unification) to reconcile, not something this increment enforces. See `src/agent/robotPresets/`.

## Tests

`pnpm test` — vitest cases covering the robot stub HTTP behaviour, the webcam panel, and the motion-summarization middleware. The before/after canvas composition is **not** covered by unit tests (jsdom has no canvas) — covered by the browser e2e instead.

## Browser e2e

`pnpm run e2e` boots the robot stub, the AG-UI server, and Vite, then drives a real Chromium (with a **fake camera**, so the webcam-capture + Before/After compose path runs without hardware) through a `move_forward → finish_task` round-trip and asserts the tool badges render and the run finalizes. It's **CI-stable**: the server runs a deterministic scripted model (`PUKEKO_FAKE_LLM=1`, `server/test-support/scriptedRobotModel.ts`) — no LLM, no network, no flake. Harness: `it-robot.js`; spec: `e2e/robot.spec.ts`.

`pnpm run e2e:live` runs the same flow against a **real LLM** (`E2E_LIVE=1`, needs an API key) — opt-in, not for default CI.

## Manual smoke-testing in the browser

For changes the e2e doesn't cover, exercise a motion tool in a real Chrome tab. Open `http://localhost:5173`, allow camera permission, and ask the agent to e.g. "turn right one cycle". The tool-call badge should expand to show a single composite image with **Before / After** labels and a divider.
